# Phase 3 — Auth Flows (Flutter + Admin Web)

## Objectives
Complete user-facing authentication on both apps plus emergency contacts setup.

## Requirements covered
FR-AUTH-1, 2, 6, 7, 8, 9, 10, 11; screens: Splash, Sign Up, Verify OTP, Login, Forgot Password, Emergency Contacts, Profile (Flutter); Admin Login, Forgot Password (web).

## Prerequisites
Phase 2 complete; api-contract approved. UI designs: none provided — ask user whether they have mockups/branding (colors, logo) before building; otherwise ask permission for a minimal neutral theme.

## Components
Flutter: `features/auth` (data: API client + secure token store; domain; presentation: screens + Riverpod controllers), `features/emergency_contacts`, `features/profile`, go_router guards (unauthenticated → login; unverified → OTP; no contacts → contacts setup).
Web: `/login`, `/forgot-password`, `/reset-password`, admin layout with route protection; non-admin rejected.

## Steps
Flutter
1. Add HTTP + secure-storage + Supabase client packages (confirm choices, D-023).
2. API client generated by hand from `api-contract.md`; base URL via build config (Q-005).
3. Sign Up form: name, student ID, `@jnu.ac.bd` email, password; client validation mirrors server.
4. OTP screen: 6 inputs, states (sent/invalid/expired/verified/rate-limited), resend countdown (60s) and disabled when limited.
5. Login/logout; persisted session with refresh handling; Splash decides route.
6. Forgot/reset password screens.
7. Emergency contacts (2–3, name+phone) shown after first login until saved; edit in Profile.
8. Profile screen (view info, logout).
Web
9. Admin login; session cookie handling per D-005; middleware blocking `/admin` routes without admin session.
10. Forgot/reset password pages.
11. Users page skeleton may wait for Phase 4/8 (not required here).

## Dependencies / integrations
Phase 2 endpoints; Supabase client for RLS reads of contacts (per D-004).

Reads/writes `emergency_contacts` (RLS: own rows; admins read). Auth endpoints from api-contract.
